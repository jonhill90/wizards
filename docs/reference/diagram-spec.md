# Diagram spec

Each wizard can carry a diagram set in `wizards/<wizard>/diagrams/`. The set is built from one JSON file, `diagrams.spec.json`. A contributor edits that file; the generator in `tools/diagrams/` turns it into SVGs and a node map. No model runs at build time, and the same spec gives the same bytes.

## Files

| File | Made by | What it is |
|---|---|---|
| `diagrams.spec.json` | a person | The source: diagram definitions and the node map |
| `<id>.svg` | `npm run diagrams` | One self-contained SVG per diagram |
| `diagrams.json` | `npm run diagrams` | Node id to diagram id, with each diagram's title, alt text and file name. A front end reads this file |

Never edit the SVGs or `diagrams.json` by hand. The tests fail if they differ from a fresh build.

## `diagrams.spec.json`

```json
{
  "diagrams": {
    "<id>": { "title": "…", "alt": "…", "spec": { "template": "zone", "items": [] } }
  },
  "nodes": { "<tree node id>": "<diagram id>" }
}
```

- `id` is a lowercase slug.
- `title` is a short name. `alt` is a sentence of at least six words that describes the picture; it becomes the start of the SVG `desc` for screen readers. The generator appends sentences on structure, arrows and colour (the legend), so do not repeat those in `alt`.
- Every diagram must be used by at least one node, and every key in `nodes` must be a node of the tree.
- Every result node needs a diagram, or must be listed in `NO_DIAGRAM_OK` in `tools/diagrams/src/check.ts`. A listed node is a stated gap and a front end keeps the previous diagram on the path.

## Templates

An item is `{ "icon": "<name>", "label": "…" }`. The icon is optional. Without one the label stands alone; the generator never draws a stand-in shape.

| Template | Fields | Shows |
|---|---|---|
| `overview` | `service`, `asks?` | The service and the three failures the wizard asks about |
| `zone` | `items`, `zones?` (2 or 3), `link?`, `badge?` | One region with availability zones, items repeated in each |
| `region` | `primary`, `secondary`, `router?`, `link?`, `secondaryKind?` (`standby`, `live`, `restore`), `primaryTitle?`, `secondaryTitle?`, `failoverLabel?` | Two regions, an optional router above them, and an arrow between them |
| `backup` | `source`, `vault`, `backupLabel?`, `restoreLabel?`, `features?`, `guard?`, `guardLabel?`, `noRestore?` | Protected data, a backup target, and the backup and restore arrows |

Zone counts and replica counts in a diagram are illustrative unless the node's cited page gives a number.

## Icons

Icon names are the keys in `tools/diagrams/icons/manifest.json`. A name that is not in the manifest fails the check. See `tools/diagrams/icons/NOTICE.md` for sources and terms.

## Commands

Run from `tools/diagrams/`:

```text
npm ci
npm run diagrams   # write the SVGs and diagrams.json
npm run check      # build in memory and fail if the committed files differ or the spec is wrong
npm test           # node:test suite
```

## In the browser

`tools/diagrams/web/diagrams.mjs` is one ES module with every icon inlined and no node imports. It is generated by `npm run diagrams` (or `npm run bundle`) and checked by `npm run check`, so never edit it.

```js
import { render, forPath } from "./tools/diagrams/web/diagrams.mjs";
const spec = await (await fetch("wizards/azure-resiliency/diagrams/diagrams.spec.json")).json();

render(spec, "sqldb-zone");                      // SVG string
render(spec, "sqldb-zone", { animate: true });   // same drawing, drawn in stage by stage
forPath(spec, ["q-service", "q-sqldb-failure", "r-sqldb-zone"], { animate: true });
// { id, title, alt, svg, fromNode } or null before any node has a diagram
```

`animate: true` adds a small `<style>`: boxes and labels fade in in drawing order and solid arrows draw themselves. It is switched off under `prefers-reduced-motion`. The shapes are identical with or without it, and the tests check that. `forPath` applies the fallback rule: a node with no diagram keeps the last one earlier on the path.

## The `scene` template (free-form drawings)

`scene` is for one-off, detailed drawings that do not fit the four wizard templates. It is not used by the wizard tree. Specs live in `tools/diagrams/examples/*.json`, one diagram entry each (`title`, `alt`, `spec`), and `npm run examples` in `tools/diagrams/` writes `examples/svg/*.svg`; `npm run check` fails if one is stale.

- `width`, `height`: the drawing area in pixels. The notes are drawn below it and add to the height.
- `groups`: outlined areas drawn in array order, so list a parent before its children. `kind` is `outline`, `blue`, `grey`, `vnet` (dashed blue boundary) or `dashed`.
- `nodes`: things at a fixed centre `x`, `y`. With `icon` (a name in `icons/manifest.json`) the node is the official icon with its label under it. With `box` it is a plain labelled box. A node with neither is a label only. Never draw a product shape yourself.
- `edges`: black arrows. Give `from`, `to` (node ids) and optional `via` bends, or exact `points`. `dashed`, `both`, `red`, `label`, `labelAt`, `n` (green numbered circle) and `nAt` are optional.
- `notes`: one sentence per numbered circle, in order. Each must state only what a cited Learn page says.


## Scenes drawn from answers (`scene-fn`)

A detailed scene that must change with the person's answers is drawn by code, not written once by hand: `{"template": "scene-fn", "scene": "sql-vm-ha-dr" | "mabs", "defaults": {...}}`. `defaults` holds what no question sets (`twoRegion` for SQL Server on VMs; `kind` of `vmware` or `agent` for MABS). The front end passes the answers of the result's shape step as `DrawParams` (`tools/diagrams/src/model.ts`): `primaryName`, `secondaryName`, `zones`, `instances`, `link`, `seeding`, `data`. `zone` and `region` diagrams take the same names and counts. Same answers, same bytes: no clock, no randomness, no model (`test/diagrams.test.ts`).

What each answer changes: SQL Server on VMs repeats the zone and the SQL replica for two or three zones, numbers the remote replica after them, names both regions, and leaves out the second region when the result has none. MABS adds the private endpoint path, the offline seeding path, or a second-server box. The numbered notes under a drawing are renumbered to match, and each states only what a Learn page says; the pages are the ones named in the tree's results (SQL Server on Azure VMs HADR overview, MABS and DPM support matrix, VMware backup with MABS, MABS protection matrix). A note that no page-by-page check has covered is listed under "Not proven" in the pull request that added it.
